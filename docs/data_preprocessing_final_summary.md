# 데이터 수집·전처리 최종 요약

작성일: 2026-08-21
상태: 데이터 전처리 단계 종료. 다음 단계(RAG/추천 로직/UI)는 시작하지 않았다.

## 1. 원천 데이터

- **중앙부처복지서비스 API** (한국사회보장정보원, `apis.data.go.kr/B554287/NationalWelfareInformationsV001`)
- **지자체복지서비스 API** (한국사회보장정보원, `apis.data.go.kr/B554287/LocalGovernmentWelfareInformations`)

두 API 모두 공공데이터포털에서 발급받은 인증키로 실제 호출해 목록조회 전체를 수집했다(각각
`data/raw/central_welfare_all.xml`, `data/raw/local_welfare_all.xml`). 행정구역 표준 데이터
(`data/processed/region_codes.csv`, `region_aliases.csv`)는 행정안전부 행정표준코드관리시스템
(code.go.kr)에서 별도 확보했다.

## 3. 후보 추출 방식

목록조회 데이터의 `servNm`(서비스명), `servDgst`(서비스요약) 두 필드를 대상으로 16개 키워드
(영양, 식사, 급식, 도시락, 밑반찬, 반찬, 식생활, 결식, 식품, 방문건강, 건강관리, 통합돌봄,
통합지원, 노인돌봄, 퇴원, 재가)를 부분 문자열 매칭했다. 매치된 서비스에 한해서만 상세조회
API를 추가 호출해 지원대상·선정기준·지원내용·신청방법·문의처 원문을 확보했다.

- 전체 5,231건(461+4,770) 중 키워드 매치 고유 서비스: **357건**

## 4. 키워드 기반 추출의 한계

- 키워드는 단순 부분 문자열 매칭이라 오탐이 존재했다(예: "영양군"이라는 지명이 '영양'과 매치,
  "인재가"라는 단어가 '재가'와 매치).
- 목록조회에는 지원대상/선정기준/지원내용 원문이 없어, 1차 스크리닝은 서비스명·요약만으로
  이뤄졌다는 한계가 있다(상세조회로 보완).
- 키워드 목록에 없는 표현(예: "중식", "간식", "부식")으로만 표현된 진짜 영양 서비스는 이 1차
  스크리닝 단계에서 애초에 걸러지지 않았을 가능성이 있다 — 이는 이번 전처리에서 확인된 구조적
  한계이며, 아래 15절에서 다시 언급한다.

## 5. 원문 재검토 방식

357건에 대해 `lifeArray`/`lifeNmArray`(생애주기) 값만으로 1차 자동 분류(`likely_senior_relevant`
98 / `likely_not_senior` 117 / `unknown` 142)한 뒤, 사람이(Claude가) 각 서비스의
`target_original`/`criteria_original`/`support_original`/`application_original` 원문을 직접
읽고 재판정했다. 이번 전처리 완료 시점까지 실제로 개별 검토를 마친 것은 **98건(1순위) + 142건
(unknown, 2순위)의 합 240건**이며, `likely_not_senior` 117건(3순위)은 이번 단계에서 검토하지
않았다(6절 참고).

## 6. senior_relation 기준 (docs/classification_criteria.md)

- `SENIOR_DIRECT`: 65세 이상/노인/어르신이 대상으로 명시
- `SENIOR_CONDITIONAL`: 고령자 전용은 아니나 연령 상한·배제 조건이 없어, 장애·저소득·재가 등
  다른 조건을 고령자도 동시에 충족할 수 있는 서비스
- `NOT_SENIOR_RELEVANT`: 고령자가 대상이 될 수 없거나(연령 상한 명시, 아동/청소년/임산부 전용 등),
  수혜자가 개인이 아니라 기관/종사자인 경우

"고령자 전용인가?"가 아니라 "고령자가 조건을 충족하면 신청 후보가 될 수 있는가?"를 기준으로 한다.

## 7. nutrition_relevance 기준

- `DIRECT_NUTRITION`: 식사·급식·도시락·반찬·식품/식재료 직접 제공, 영양상담/영양교육
- `SUPPORTIVE_NUTRITION`: 식비·식재료 바우처, 통합돌봄의 명시적 일부로 포함된 식사·영양지원
- `NOT_NUTRITION_RELEVANT`: 병원동행·취업·일반 의료·기관운영비 등

두 축(senior_relation × nutrition_relevance)은 독립 판단하며, 어느 한 축이라도 부정적이면
최종 EXCLUDE한다. 이 원칙은 이번 최종화 단계에서 NEEDS_REVIEW 3건(행려자 급식비 관련)을
확정할 때도 그대로 적용했다 — "급식비"라는 단어가 있어도 일회성 긴급구호의 부수 항목이라
`NOT_NUTRITION_RELEVANT`로 재조정해 EXCLUDE했다(결정적 근거: 서비스 원문에 "평택시민 신청
불가"가 명시돼, 이 사업이 지역사회 거주자 대상이 아님이 확인됨).

## 8. UNKNOWN 142건 검토 과정

`senior_relevance=unknown`(생애주기 정보 없어 1차 자동판정 불가) 142건을 4개 배치로 나눠
검토했다.

- **batch01(30건)**: 파일 순서상 앞 30건. 산모·신생아 서비스가 11건(37%) 섞여 있었다.
- **batch02(30건)**: 순서상 다음 30건. 산모·신생아 비중이 19건(63%)으로 더 높아짐 — 편중 확인.
- **batch03(40건)**: 남은 82건의 분포를 먼저 확인(산모·신생아 50건=61%)한 뒤, 비산모신생아
  32건 전부 + 산모신생아 8건(체계적 표집)으로 층화 추출. INCLUDE 비율이 38%로 급등 —
  batch01·02의 낮은 INCLUDE 비율이 표본 편중 때문이었음을 뒷받침.
- **batch04(42건, 마지막)**: 나머지 전부(사실상 산모·신생아 단일 유형)를 실제로 전부 읽고
  재확인. 예외 없이 전부 EXCLUDE(NOT_SENIOR_RELEVANT).

## 14. 데이터 품질 문제

- 검토 과정에서 원문 자체(공공데이터포털 API 응답)에서 다음과 같은 문제를 발견했다(원문은
  수정하지 않고 `data_quality_note`에만 기록):
  - 더미(placeholder) 전화번호(`033-000-0000`)
  - 중복 연락처, 연락처 누락
  - 오탈자("보거놋"→"보건소")
  - target/criteria/support/application 4개 필드가 완전히 동일한 문장 반복
  - 지원대상 인원수 불일치(target 20세대 vs support 25가구)
  - 사업명과 실제 지원내용 불일치(사업명은 "퇴원환자 지역사회 연계사업"인데 원문에 "급여서비스
    없음"이라고 명시된 사례)
  - 지역 필드 누락(사업명·문의처로는 명백히 특정 시 사업인데 sigungu 필드가 비어있는 경우)
  - 사실상 동일한 사업이 하위 관할(출장소 등)별로 중복 등록된 것으로 보이는 경우
- **이 모든 문제는 원본 API 데이터에서 발견된 것이며, 이번 전처리 작업 과정에서 새로 만들어진
  문제는 발견되지 않았다** — 병합 스크립트가 원문 보호 필드 변경 0건임을 자동 검증했다.
- `welfare_services_final.csv` 85건 중 `data_quality_note`가 기록된 건: **3건**(모두 batch02·03
  단계에서 발견, 최종 INCLUDE 후보에 한정한 수치이며 EXCLUDE 처리된 건까지 포함하면 더 많다).
- 최종화 과정에서 자동 모순 탐지기가 1건(WLF00001291, "meal_support_flag=true인데 원문에 식사
  단어가 안 보임")을 플래그했으나, 직접 원문을 재확인한 결과 지원내용에 **"중식 제공"**이 명시돼
  있어 실제로는 모순이 아니었다(자동 탐지기의 키워드 목록이 "중식"을 포함하지 않았던 것이 원인).
  이 사례는 자동 탐지 로직 자체의 한계를 보여주며, 사람의 최종 확인이 필요함을 재확인시켜준다.

## 15. 데이터의 한계

1. **분류 세부도가 균일하지 않다.** 최종 INCLUDE 85건 중 54건(1순위 최초 검토분)은
   `senior_relation`, `nutrition_relevance`, `service_type_primary`, `min_age`,
   `disability_required` 등 세부 이용조건 필드가 채워져 있지 않다. 이 필드들은 검토 방법론이
   발전한 이후(11건 재판정 및 unknown 142건 검토)에만 기록됐다. 나머지 31건(신규)만 이 필드가
   채워져 있다.
2. **`min_age`/`disability_required`/`low_income_required`/`single_household_required`/
   `homebound_or_mobility_condition`/`eligibility_summary`/`support_summary` 필드는 unknown
   142건 검토에서 전혀 채우지 못했다.** batch01~04 검토는 senior_relation_v2·nutrition_relevance·
   service_type 수준까지만 판정했고, 이 세부 Boolean/요약 필드는 별도 원문 재분석이 필요하다 —
   추측해서 채우지 않고 빈 값으로 남겼다.
3. **키워드 스크리닝 단계(357건 추출)에서 이미 누락된 서비스가 있을 수 있다.** 16개 키워드에
   없는 표현("중식", "부식", "간식" 등)으로만 서술된 서비스는 애초에 후보 목록(357건)에 들지
   못했을 가능성이 있다. 예를 들어 이번 최종 INCLUDE 중 하나(WLF00001291)의 지원내용은
   "중식 제공"인데, 이 서비스가 후보에 포함된 것은 다른 키워드("급식","영양","재가")가 함께
   매치됐기 때문이지 "중식"이라는 단어 때문이 아니다 — 만약 이 서비스의 서비스명/요약에 매치된
   다른 키워드가 전혀 없었다면 애초에 후보에도 들지 못했을 것이다.
4. **`likely_not_senior` 117건(3순위)은 이번 전처리에서 전혀 검토되지 않았다.** 이 중 실제로는
   고령자와 관련된 서비스가 섞여 있을 가능성을 배제할 수 없다.
5. **지역명 표준화가 완전히 검증되지 않았다.** `region_codes.csv`의 표준 시도명과 API 응답의
   `ctpvNm` 값이 100% 일치하는지 전수 대조하지 않았다(예: "전남광주통합특별시" 표기는 일치를
   확인했으나 전체 85건에 대한 조인 테스트는 이번 단계에서 하지 않았다).
6. **원문 텍스트의 품질(오탈자, 중복, 불일치)은 원본 API 데이터의 한계이며, 우리가 통제할 수
   없는 부분이다.**

## 16. 향후 업데이트 시 주의사항

1. `welfare_candidates_reviewed.csv`가 이제 **모든 후속 작업의 정본(source of truth)**이다.
   `service_id`를 기본키로 사용해야 한다.
2. 3순위(`likely_not_senior` 117건)를 검토하려면 이번과 동일하게
   `docs/classification_criteria.md`를 그대로 적용하고, `senior_relation`/`nutrition_relevance`가
   비어있는 새 배치를 만들어 채운 뒤 `src/data_collection/finalize_welfare_dataset.py`와 유사한
   병합 스크립트로 반영해야 한다(이번 스크립트를 그대로 재사용할 수는 없다 — 배치 소스가 다름).
3. 1순위 54건(세부 필드 미기재)을 보완하려면, 해당 54건의 `service_id` 목록을 뽑아 원문을 다시
   읽고 `min_age` 등 세부 필드를 채우는 별도 작업이 필요하다. 이번 단계에서는 하지 않았다.
4. 원본 API 데이터(`data/raw/*.xml`)는 재수집 없이 그대로 보존돼 있으므로, 세부 필드 보완이나
   재검토가 필요할 때 새로 API를 호출할 필요 없이 기존 `application_original` 등 원문을 다시
   읽으면 된다.
5. 이 데이터셋은 **"신청 가능성을 확인해볼 후보"를 위한 것이며 수급자격을 확정하지 않는다**는
   원칙이 이후 추천 로직/UI 설계에도 그대로 유지돼야 한다.
