### 두 복지서비스 API 심층 질문에 대한 답
1. 전체 서비스 목록 조회 가능한가 → **가능** (목록조회 오퍼레이션, `numOfRows` 최대 500)
2. 서비스 상세조회 가능한가 → **가능** (`servId` 기반)
3. 지원대상 제공하는가 → **O** (자연어 텍스트, `tgtrDtlCn`/`sprtTrgtCn`)
4. 선정기준 제공하는가 → **O** (`slctCritCn`)
5. 신청방법 제공하는가 → **O** (중앙: `applmetList`, 지자체: `aplyMtdNm`/`aplyMtdCn`)
6. 문의처 제공하는가 → **O** (`inqplCtadrList`)
7. 지역정보 제공하는가 → **중앙: X / 지자체: O**(`ctpvNm`, `sggNm`)
8. 고령자 관련 서비스만 필터링 가능한가 → **부분적으로 가능**. `lifeArray`(생애주기)에 "노년" 코드가 있을 것으로 추정되나 **코드표(첨부 doc)를 열람하지 못해 확정 불가**
9. 식사/영양/돌봄 서비스만 필터링 가능한가 → **`searchWrd`(검색어)로 가능**. "영양", "식사", "돌봄", "급식" 등을 키워드로 검색하면 됨. 단, 이 방식은 카테고리 필터가 아니라 텍스트 검색이라 재현율(recall)이 완벽하지 않을 수 있음
10. 검색어 기반 검색이 가능한가 → **가능** (`searchWrd` + `srchKeyCode`로 제목/내용/제목+내용 범위 지정)
11. 지역코드로 조회할 수 있는가 → **지역명(문자열)으로 조회**. `region_code`(법정동코드 숫자)가 아니라 `ctpvNm`/`sggNm` **명칭**이 파라미터임 — 법정동코드 API의 코드값과 문자열이 다를 경우 별도 매핑 로직 필요
12. 한 번에 받을 수 있는 데이터 수 제한 → 중앙부처: 명시 없음(옵션), 지자체: 명시 없음. **중앙부처 목록조회의 `numOfRows` 최대값 500 확인됨**, 지자체는 최대값 명시 안 됨(**미확인**)
13. pagination 필요한가 → **필요**. `pageNo`+`numOfRows` 표준 페이지네이션
14. 상세조회에 필요한 service ID → `servId` (목록조회 응답의 `servId` 값을 그대로 사용)
15. XML만 제공하는가 → 페이지 문서상 **XML만 명시**. JSON 옵션이 명시적으로 확인되지 않음(**미확인**, 실제 호출 전 확정 불가)
16. Python에서 사용하기 쉬운가 → REST + XML이므로 `requests` + `xml.etree.ElementTree`(또는 `xmltodict`)로 무난하게 처리 가능. 공식 예제코드에 Python이 없고 Java/JS/PHP/Curl 등만 제공된다는 점은 다소 불편(검색 결과에서 확인, Python 없음)

**"이 두 API만으로 핵심 복지서비스 DB를 구축할 수 있는가?" → PARTIALLY**

부족한 부분:
- **영양사 참여 여부**는 어떤 필드에도 없다. `alwServCn`(지원내용) 자연어 안에서 "영양사"라는 단어를 검색해야 하며, 언급이 없다고 "참여 안 함(false)"으로 단정할 수 없다 → `nutritionist_involvement`는 원문(복지로 상세페이지 등) 대조 없이는 항상 `not_specified`로 처리해야 함
- **고령자 필터 코드값**을 확정하지 못해, `lifeArray`만으로 "65세 이상"을 걸러낼 수 있는지 아직 검증 안 됨(코드표 doc 필요)
- **지자체 서비스가 실제로 몇 개 시군구·몇 건이나 등록돼 있는지**는 호출 전까지 알 수 없음(전국 226개 시군구를 다 커버하는지는 불확실)
- 두 API 모두 **자연어 필드가 데이터의 핵심**이라, `min_age`/`max_age`/`income_rule` 같은 구조화된 Boolean/숫자 필드는 결국 이 텍스트를 사람(또는 LLM)이 읽고 채워야 한다 — API가 이 작업을 대신해주지 않는다

**결론(비교)**:
| 방안 | 장점 | 단점 |
|---|---|---|
| API 신청 후 실시간 조회 | 행정구역 변경 시 자동 반영, 공식 코드 확보 | 활용신청 승인 대기, 호출 관리 비용, 이번 MVP엔 과함 |

### 7. 이 데이터 조합으로 실제 MVP가 가능한가?

**부분적으로 가능하다(PARTIALLY).**

가능한 것:
- 지자체복지서비스 API의 `ctpvNm`/`sggNm` + 중앙부처복지서비스 API로 "거주지역 기반 서비스 후보 목록"을 구조적으로 만들 수 있다.
- `sprtTrgtCn`/`tgtrDtlCn`(지원대상), `slctCritCn`(선정기준), `alwServCn`(지원내용), `aplyMtdNm`/`applmetList`(신청방법), `inqplCtadrList`(문의처), `servDtlLink`(공식 근거 URL)가 모두 존재하므로 요청하신 안내 항목(후보 이유/지원대상/선정기준/지원내용/신청방법/문의처/담당기관/공식근거) 중 **"영양사 참여 여부"를 제외한 전부**를 API 응답으로 채울 수 있다.

부족한 것(반드시 사람의 검증 또는 별도 작업이 필요):
- **영양사 참여 여부**는 API에 필드가 없어 `alwServCn` 등 자연어를 읽고 판단해야 하며, 언급이 없으면 `not_specified`로 남겨야 한다(추측 금지 원칙 준수).
- **age/income을 숫자·Boolean으로 구조화하는 작업**은 API가 대신해주지 않는다. 자연어(`tgtrDtlCn`/`slctCritCn`)를 사람(또는 LLM 보조)이 읽고 `min_age`/`low_income_required`(true/false/unknown) 등으로 변환해야 한다.
- **`service_type`(6개 분류)에 대응하는 공식 코드값**이 존재하는지(코드표 미확인)라 자동 분류가 아니라 서비스명/설명을 보고 수작업 분류가 필요할 가능성이 높다.
- 지자체복지서비스 API가 **전국 226개 시군구를 실제로 다 커버하는지는 호출 전까지 알 수 없다** — 커버리지가 낮으면 이전 조사에서 지적한 "지자체별 급식지원사업 전국 통합 출처 없음" 문제가 완전히 해결되지 않을 수 있다.

**요약**: 이 두 API는 "MVP에 필요한 최소 데이터 조합"의 핵심 뼈대이지만, 그 자체로 `service_type`, `nutritionist_involvement`, 정량화된 대상조건까지 완성해주지는 않는다. API로 후보 목록과 원문 근거를 자동 확보한 뒤, **사람이(또는 Claude가 원문을 다시 읽어) 최종 필드를 채우는 반자동(SEMI_AUTO) 파이프라인**이 될 것으로 판단한다.
